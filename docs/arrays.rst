============
Array Syntax
============
(`interactive example <https://tbuli.github.io/teahouse/lab/index.html?path=2DPGA%2Fex_2dpga_boids.ipynb>`_)

Kingdon was designed to be agnostic to coefficient types, and therefore it is compatible with
popular array types such as :code:`numpy` or :code:`torch`.
In order to facilitate working with multivectors over arrays, :code:`kingdon` fully
supports array indexing and masking, which results in compact yet performant code.

.. note::
    These design choices were made in part because working with a multivector of arrays is *much* faster
    than working with an array of multivectors.

TL;DR
-----
To get started with :code:`kingdon` on arrays types straight away, we highlight the most important steps here.

1. Create your algebra with a :code:`values_asarray` function that always casts multivectors back to arrays.

.. code-block::
    :caption: NumPy

    >>> alg = Algebra.fromname("3DPGA", values_asarray=np.asarray)

.. code-block::
    :caption: PyTorch

    >>> def asarray(values):
    >>>     return torch.stack(values) if values and all(isinstance(v, torch.Tensor) for v in values) else values
    >>> alg = Algebra.fromname("3DPGA", values_asarray=asarray)

:code:`np.asarray` expects all coefficients of a multivector to have the same shape, which is the common
case and also the fastest option; it raises a :code:`ValueError` if they do not.
See :ref:`Inhomogeneous output` for when and how to deal with such coefficients.
The :code:`torch` version needs a guard because :code:`torch` has no object dtype: basis blades carry
plain python numbers and symbolic multivectors carry expressions, neither of which :code:`torch.stack`
accepts. Those are passed through as a list instead, which is what kingdon does by default anyway.

2. (Optional) Provide a wrapper function upon algebra creation that is always applied to the code generated by
   kingdon, after kingdon has already done its symbolic optimization and cse, to make it even faster.

.. code-block::
    :caption: torch.compile

    >>> alg = Algebra.fromname("3DPGA", values_asarray=asarray, wrapper=torch.compile)

3. Write vectorized code whenever possible. :code:`kingdon` multivectors are not themselves array types, but they enable much of the same programming paradigm.

For example, suppose we want to project :math:`N` points on :math:`M` lines using the projection operator :code:`@`.
You can add a new dimension to your multivector (and thus the underlying array) using the syntax :code:`points[:, None]`.
You can use this to keep your algorithm focused on the geometry, while simultaniously being compatible with the array paradigm:

.. code-block::

    >>> N, M = 5, 3
    >>> points = alg.point(np.random.rand(3, N))
    >>> lines = alg.bivector(np.random.rand(6, M)).normalized()
    >>> projected_points = points[:, None] @ lines[None, :]
    >>> projected_points.shape
    (5, 3)

The projection of point 1 on line 2 is now available as :code:`p12 = projected_points[1, 2]`.

Or as another example; suppose we have the point cloud :code:`points` above, and we want to find all
points within a given radius from a particular point :code:`O`.
This can be done using the standard masking syntax:

.. code-block::

    >>> O = alg.point([0, 0, 0])
    >>> l = (points & O)                 # Join all p in point with O in one high level statement
    >>> l.shape
    (5,)
    >>> d = l.norm()                     # Length of the line segments [p, O] for p in points
    >>> target_points = points[d.e < 1]  # all points within the unit sphere

You see that our algorithm expresses the geometry of the problem very compactly; the broadcasting is all
done automatically by the array types we are working over.

The indexing syntax of the python array API is also supported. As an example,
consider we have a mesh, defined by an :code:`(N, 3)` float array :code:`vertices` with N vertex coordinates,
and an :code:`(M, 3)` integer array :code:`faces` where the integers in the range :math:`[0, N)` are the indices of
which three vertices make a given face in the mesh.
Then if we make a point :code:`v` of shape :code:`(N,)` from :code:`vertices`,
the :code:`faces` array can be applied as :code:`v[faces]` to form the :code:`(M, 3)` array of faces,
on which we can do operations:

.. code-block::

    >>> vertices, faces = load_obj(...)  # Load some obj mesh file to get N vertices and M faces
    >>> v = (pga3d.blades.e0 + pga3d.evector(vertices.T)).dual()  # algebraic construction of PGA points.
    >>> v.shape
    (N,)
    >>> facets = v[faces]
    >>> facets.shape
    (M, 3)
    >>> planes = facets[..., 0] & facets[..., 1] & facets[..., 2]
    >>> planes.shape
    (M,)
    >>> areas = 0.5 * planes.norm()  # The areas of the triangles is half that of the planes
    >>> area = areas.map(np.sum)
    >>> volume = np.sum(planes.e0)


Lastly, :code:`kingdon` is also compatible with :code:`einops`.
In the einops patterns you only make reference to the non-blade dimensions of the multivector,
in accordance with what you would expect on the basis of the shape of the multivector.


.. code-block::
    :caption: rearrange

    >>> from einops import rearrange
    >>> from kingdon import Algebra
    >>> import kingdon.einops_backend
    >>> import numpy as np
    >>>
    >>> alg = Algebra(2)
    >>> x = alg.vector(np.random.rand(2, 3, 4))
    >>> x.shape
    (3, 4)
    >>> y = rearrange(x, 'a b -> b a')
    >>> y.shape
    (4, 3)

.. code-block::
    :caption: reduce

    >>> from einops import reduce
    >>>
    >>> z = reduce(x, 'a b -> a', 'mean')
    >>> z.shape
    (3,)

.. code-block::
    :caption: pack & unpack

    >>> from einops import pack, unpack
    >>>
    >>> a = alg.vector(np.zeros([2, 3, 5]))
    >>> b = alg.vector(np.zeros([2, 3, 7, 5]))
    >>> packed, ps = pack([a, b], 'j * k')
    >>> packed.shape
    (3, 8, 5)
    >>> a2, b2 = unpack(packed, ps, 'j * k')
    >>> a2.shape == a.shape and b2.shape == b.shape
    True

.. code-block::
    :caption: einsum

    >>> from einops import einsum
    >>>
    >>> vec = alg.vector(np.random.randn(2, 10, 10))
    >>> trace = einsum(vec, 'i i ->')
    >>> trace.shape
    ()
    >>> weight = np.random.randn(10, 20)
    >>> matmul = einsum(vec, weight, 'i j, j k -> i k')
    >>> matmul.shape
    (10, 20)


That is it! If you are interested in more details, the rest of this page explains all of this and more in full detail.

The Shape of MultiVectors
-------------------------

Ordinarily multivectors are zero dimensional, and have no length.
For example, in :math:`\mathbb{R}_3` we have

.. code-block::

    >>> from kingdon import Algebra
    >>> import numpy as np
    >>>
    >>> alg = Algebra(3)
    >>> xvals = np.random.rand(3)  # e1, e2, e3 coefficients
    >>> x = alg.vector(xvals)
    >>> x.shape
    ()

Now if we look at :code:`x.shape`, we see that it is :code:`()`, even though :code:`xvals.shape` is :code:`(3,)`.
This reflects that :code:`x` is a single vector, and therefore not iterable. You might have expected
iteration over a multivector to iterate over its coefficients, but in :code:`kingdon` multivectors are
treated as geometric numbers, similar to how complex numbers are treated in complex analysis.
If we attempt to retrieve the length of :code:`x` a :code:`TypeError` is raised, consistent with the fact
that 0-dimensional multivectors are not iterable:

.. code-block::

    >>> len(x)
    TypeError: len() of unsized 0-dimensional multivector

.. note::
    If you need to iterate over the coefficients anyway use :code:`x.map` to map a function on all the
    coefficients of the multivector.
    For individual access, use attributes access instead, e.g. :code:`x.e1` returns the
    :math:`\mathbf{e}_1` coefficient.

Now lets make a collection of :math:`N` vectors, and see what changes:

.. code-block::

    >>> N = 5
    >>> xvals = np.random.rand(3, N)
    >>> x = alg.vector(xvals)
    >>> x
    [0.37454012 0.95071431 0.73199394 0.59865848 0.15601864] 𝐞₁ + [0.15599452 0.05808361 0.86617615 0.60111501 0.70807258] 𝐞₂ + [0.02058449 0.96990985 0.83244264 0.21233911 0.18182497] 𝐞₃
    >>> x.shape
    (5,)
    >>> len(x)
    5

Hence, we see that the length of the multivector is :code:`5`, and therefore we can iterate over the
multivector to get the individual vectors in :code:`x`:

.. code-block::

    >>> for vector in x:
    >>>     print(vector)
    0.375 𝐞₁ + 0.156 𝐞₂ + 0.0206 𝐞₃
    0.951 𝐞₁ + 0.0581 𝐞₂ + 0.97 𝐞₃
    0.732 𝐞₁ + 0.866 𝐞₂ + 0.832 𝐞₃
    0.599 𝐞₁ + 0.601 𝐞₂ + 0.212 𝐞₃
    0.156 𝐞₁ + 0.708 𝐞₂ + 0.182 𝐞₃

A huge benefit of multidimensional multivectors is that the resulting code is very compact.
For example, to compute the norm of (all vectors in) :code:`x`, we simply do

.. code-block::

    >>> d = x.norm()
    >>> d
    [0.40624908 1.35939565 1.4067825  0.87453939 0.74750847]

Masking & Indexing
------------------

Now suppose we were only interested in those vectors with :math:`d > 1`,
we can use numpy's masking syntax to do

.. code-block::

    >>> large_x = x[d.e > 1]
    >>> large_x
    [0.95071431 0.73199394] 𝐞₁ + [0.05808361 0.86617615] 𝐞₂ + [0.96990985 0.83244264] 𝐞₃

First, :code:`d.e` selects the scalar coefficient of the multivector :code:`d`.
Then, :code:`d.e > 1` creates the boolean array :code:`[False  True  True False False]`, indicating
which elements satisfy the condition. Lastly, :code:`x[d.e > 1]` passes this condition on to the
multivector coefficients, which are all arrays of shape :code:`(5,)`.
Importantly, :code:`kingdon` passes the thing between the square brackets (:code:`x[...]`) on to the
coefficients *unseen*, thus enabling not only numpy style indexing and masking, but also
any other magic your coefficients might do with :code:`__getitem__` overloading.

Mesh
~~~~

As an example of this powerful syntax, consider a mesh defined by two arrays:

- :code:`vertices`: a float array of shape :code:`(N, 3)` that defines the :math:`(x, y, z)`
  coordinates of :math:`N` vertices.
- :code:`faces`: an integer array of shape :code:`(M, 3)` that defines the topology of the faces
  of the mesh. The integers are indices into the :code:`vertices` array, and hence in the range :math:`[0, N)`.


In order to convert the vertices to multivectors (in 3DPGA), we need to transpose :code:`vertices` such that the
:code:`x,y,z`-coordinates can be matched up with the :math:`\mathbf{e}_i^*` directions:

.. code-block::

    >>> pga3d = Algebra.fromname("3DPGA")
    >>> v = (pga3d.blades.e0 + pga3d.evector(vertices.T)).dual()
    >>> v.shape
    (N,)

Suppose we now want to alternativelly have a datastructure of shape :math:`(M, 3)`,
which explicitelly contains the coordinates of the vertices for every face, similar to how
`STL files <https://en.wikipedia.org/wiki/STL_(file_format)#ASCII>`_ are structured.
This is now as simple as

.. code-block::

    >>> facets = v[faces]
    >>> facets.shape
    (M, 3)

In order to compute the area and (signed) volume of the mesh we can use numpy's indexing
syntax to first create all planes,

.. code-block::

    >>> planes = facets[..., 0] & facets[..., 1] & facets[..., 2]
    >>> planes.shape
    (M,)

from which we can then compute the area:

.. code-block::

    >>> areas = planes.norm()
    >>> area = areas.map(np.sum)

and the volume:

.. code-block::

    >>> volume = np.sum(planes.e0)

Yes, we just computed the signed volume directly from the coefficient of :math:`\mathbf{e}_0`!
This coefficient is the signed volume a plane makes with the origin, and by adding this up for all
planes we find the signed volume of the mesh. For more info, see `this paper <https://arxiv.org/abs/2511.08058>`_.

How to stay in hyper-space
~~~~~~~~~~~~~~~~~~~~~~~~~~

Kingdon's GA operations have a subtle consequence for the type of the `values()` atribute which you may want to avoid.
Reconsider the example of the computation of all the planes of the mesh:

.. code-block::

    >>> type(facets.values())
    <class 'numpy.ndarray'>
    >>> planes = facets[..., 0] & facets[..., 1] & facets[..., 2]
    >>> type(planes.values())
    <class 'list'>
    >>> type(planes.values()[0])
    <class 'numpy.ndarray'>

So even though we started with numpy arrays, after a binary operation we will have a list of numpy arrays instead.
There are two ways to avoid this:
1. Provide a :code:`values_asarray` function that ensures that ensures the values after computation are always cast back to a numpy array:

.. code-block::

    >>> alg = Algebra(3, 0, 1, values_asarray=np.asarray)

2. Preallocate the result array and tell kingdon to use it:

.. code-block::

    >>> pvals = np.empty((4, N))
    >>> planes = alg.vector(pvals)
    >>> planes.set(v[0] & v[1] & v[2])
    >>> type(planes.values())
    <class 'numpy.ndarray'>

Inhomogeneous output
~~~~~~~~~~~~~~~~~~~~

:code:`np.asarray` requires all coefficients of the result to have the same shape.
That is the case for the vast majority of computations, and it is also the fastest option, since the
coefficients can be copied into the output array as they are.
If you deliberately mix shapes however, for example by adding a scalar multivector to a multivector of
arrays, :code:`np.asarray` raises a :code:`ValueError` and you have to broadcast the coefficients
against each other yourself:

.. code-block::

    >>> def asarray(values):
    >>>     return np.asarray(np.broadcast_arrays(*values))
    >>> alg = Algebra(3, 0, 1, values_asarray=asarray)

Do not reach for this by default. :code:`np.broadcast_arrays` adds a fixed overhead to *every* operation,
which is why it is not what we recommend in the TL;DR: for a multivector with eight scalar coefficients,
always broadcasting costs about 8.9 μs per call against 0.8 μs for plain :code:`np.asarray`
(CPython 3.12, numpy 2.3).
Should you want both, the fast path when the shapes agree and broadcasting when they do not, then let the
exception decide instead of inspecting the shapes up front:

.. code-block::

    >>> def asarray(values):
    >>>     try:
    >>>         return np.asarray(values)
    >>>     except ValueError:  # Coefficients of different shapes.
    >>>         return np.asarray(np.broadcast_arrays(*values))

An untaken :code:`try` is free in CPython 3.11 and up, so this costs nothing over plain
:code:`np.asarray` when the shapes agree (0.9 μs), and about 8% extra when they do not.
Calling :code:`np.shape` on every coefficient up front to decide the same thing is far more
expensive at 13.9 μs, because you then pay for the check on every single operation.

Avoid for loops
~~~~~~~~~~~~~~~

A well known disadvantage of Python are its slow for-loops. If possible, it is preferable to use only vectorized methods.
In order to avoid for loops we sometimes have to add a new axis, such that we can take advantage of numpys broadcasting
rules.
For example, suppose we want to project :math:`N` points on :math:`M` lines using the projection operator :code:`@`.

.. code-block::

    >>> N, M = 3, 5
    >>> points = pga.point(np.random.rand(3, N))
    >>> lines = pga.bivector(np.random.rand(6, M)).normalized()
    >>> projected_points = points[:, None] @ lines[None, :]
    >>> projected_points.shape
    (3, 5)


 The result is identical to :code:`stack([p @ lines for p in points])`, but leveraging array magic is
 obviously much faster.

 This example shows the power of the :code:`kingdon` syntax: it combines the power of GA with the power of the
 python array API.

Einops
------

:code:`kingdon` is compatible with `einops <https://einops.rocks/>`_, enabling powerful tensor
manipulations directly on multivectors, whose coefficients are in turn tensors/arrays of one
of the supported backends
(`numpy <https://numpy.org/>`__,
`PyTorch <https://pytorch.org/>`__,
`JAX <https://jax.readthedocs.io/>`__,
`CuPy <https://cupy.dev/>`__,
`MLX <https://github.com/ml-explore/mlx>`__,
`tinygrad <https://github.com/tinygrad/tinygrad>`__,
`Paddle <https://www.paddlepaddle.org.cn/en>`__,
`Flax <https://flax.readthedocs.io/>`__).
To use it, simply import the backend before any einops calls:

.. code-block::

    >>> import kingdon.einops_backend

This registers the kingdon backend with einops that enables the application of einops operations on multivectors.
As we have seen in this section, the first dimension of the multivector is always the coefficients,
and is therefore not available for  manipulation by the einops operations, as this would not be geometrically meaningful.
So in your :code:`einops` operations, be sure to ignore the first dimension; it is not yours to play with.

Rearrange
~~~~~~~~~

:code:`rearrange` reshapes and reorders the batch dimensions of a multivector:

.. code-block::

    >>> from einops import rearrange
    >>> from kingdon import Algebra
    >>> import kingdon.einops_backend
    >>> import numpy as np
    >>>
    >>> alg = Algebra(2)
    >>> x = alg.vector(np.random.rand(2, 3, 4))
    >>> x.shape
    (3, 4)
    >>> y = rearrange(x, 'a b -> b a')
    >>> y.shape
    (4, 3)

Notice how the einops pattern :code:`'a b -> b a'` only makes reference to the non-blade
dimensions of the multivector, but not the (first) blade dimensions.
This is by design, and ensures that the result remains a vector.

Reduce
~~~~~~

:code:`reduce` applies a reduction (e.g. mean, sum, max) along specified batch dimensions:

.. code-block::

    >>> from einops import reduce
    >>>
    >>> y = reduce(x, 'a b -> a', 'mean')
    >>> y.shape
    (3,)

Again, notice how the einops pattern :code:`'a b -> a'` only makes reference to the non-blade
dimensions of the multivector.

Repeat
~~~~~~

:code:`repeat` is the inverse of :code:`reduce`: it repeats a multivector along new or
existing batch dimensions. Every coefficient is repeated identically, so the result is
still a multivector of the same type:

.. code-block::

    >>> from einops import repeat
    >>>
    >>> y = repeat(x, 'a b -> a b c', c=5)
    >>> y.shape
    (3, 4, 5)
    >>> y = repeat(x, 'a b -> (rep a) b', rep=2)
    >>> y.shape
    (6, 4)

Pack & Unpack
~~~~~~~~~~~~~

:code:`pack` concatenates multivectors with compatible shapes along a wildcard axis,
and :code:`unpack` reverses the operation:

.. code-block::

    >>> from einops import pack, unpack
    >>>
    >>> a = alg.vector(np.ones([2, 3, 5]))
    >>> b = alg.vector(np.ones([2, 3, 7, 5]))
    >>> packed, ps = pack([a, b], 'j * k')
    >>> packed.shape
    (3, 8, 5)
    >>> a2, b2 = unpack(packed, ps, 'j * k')
    >>> a2.shape == a.shape and b2.shape == b.shape
    True

Again, notice how the einops patterns :code:`'j * k'` only make reference to the non-blade
dimensions of the multivectors as these need to match the blades of the multivector and can therefore not be modified.

The multivectors that are packed together must all be of the same type. Their keys however may differ:
the result gets the union of the keys of its inputs, and a blade that an input does not have simply contributes zeros.
So packing a general vector together with one that only lives on :math:`\mathbf{e}_1` gives the
latter an explicit zero on :math:`\mathbf{e}_2`:

.. code-block::

    >>> c = alg.vector(e1=np.ones([3, 7, 5]))
    >>> c.keys()
    (1,)
    >>> packed, ps = pack([a, c], 'j * k')
    >>> packed.keys()
    (1, 2)
    >>> packed.shape
    (3, 8, 5)
    >>> a2, c2 = unpack(packed, ps, 'j * k')
    >>> c2.keys(), c2.shape
    ((1, 2), (3, 7, 5))
    >>> bool(np.all(c2.e2 == 0))
    True

Those zeros are made from the coefficients that the sparse multivector does have, in such a way that they carry
the same dtype and live on the same device, whichever array type you are working over.

Einsum
~~~~~~

:code:`einsum` performs einstein summation on multivectors, useful for e.g. traces or
matrix multiplications over batch dimensions.
Just like the other :code:`einops` functions, the pattern only makes reference to
:code:`mv.shape` and thus ignores the coefficient dimension: the summation is performed
blade by blade.

.. code-block::

    >>> from einops import einsum
    >>>
    >>> vec = alg.vector(np.random.randn(2, 10, 10))
    >>> trace = einsum(vec, 'i i ->')
    >>> trace.shape
    ()
    >>> weight = np.random.randn(10, 20)
    >>> matmul = einsum(vec, weight, 'i j, j k -> i k')
    >>> matmul.shape
    (10, 20)

Because the summation happens blade by blade, all multivectors in an :code:`einsum` must
have the same keys (i.e. basis blades). The exception are scalars, which multiply every
blade and can therefore be combined with any multivector:

.. code-block::

    >>> s = alg.scalar(np.random.randn(1, 10))
    >>> scaled = einsum(vec, s, 'i j, j -> i j')
    >>> scaled.shape
    (10, 10)

To multiply two multivectors of different types, use one of the products of the algebra
instead, e.g. :code:`vec * bivec`. Do mind that such a product multiplies the underlying
arrays elementwise (with the usual broadcasting rules), and cannot be combined with
:code:`einsum`: there is no pattern which contracts array dimensions and performs a
geometric product at the same time.

.. note::
    :code:`einops` selects its backend on the basis of the first argument only, so when mixing
    multivectors with e.g. :code:`numpy` arrays, make sure a multivector comes first.
    Put the array first and :code:`einops` hands the whole expression to :code:`numpy`, which
    silently degrades the multivector into an object array instead of raising:
    :code:`einsum(weight, vec, 'i j, i -> j')` returns an :code:`ndarray` of multivectors,
    not a multivector of arrays.

Parse_shape & asnumpy
~~~~~~~~~~~~~~~~~~~~~

:code:`parse_shape` names the array dimensions of a multivector, which is convenient to
feed the lengths of the batch dimensions back into another einops call:

.. code-block::

    >>> from einops import parse_shape
    >>>
    >>> parse_shape(x, 'a b')
    {'a': 3, 'b': 4}

:code:`asnumpy` converts the coefficients of a multivector to :code:`numpy` arrays, e.g. to
get a multivector over :code:`torch` tensors back to the cpu:

.. code-block::

    >>> from einops import asnumpy
    >>>
    >>> y = asnumpy(x)
    >>> y.shape
    (3, 4)

For other backends :code:`asnumpy` returns a :code:`numpy.ndarray`, but for :code:`kingdon` it
returns a multivector whose coefficients are :code:`numpy.ndarray`, since a multivector is a
container of arrays rather than an array itself. Call :code:`y.values()` if you need the
underlying array, which does have the blades as its first dimension.
